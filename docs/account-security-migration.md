# 認証・RA権限の更新（2026-09-05）

今回の変更はアプリ側の修正とデータベースの修正を合わせて反映します。リポジトリにSQLを保存しただけでは、稼働中のデータベースは変更されません。

## 適用対象と順序

1. 対象環境を確認し、現在のバックアップと「現在のRA」の一覧を確認します。
2. 既存環境で `20260829130000_add_institutional_accounts.sql` が適用済みであることを確認します。新規環境では `schema.sql` と既存の追加マイグレーションが前提です。
3. `supabase/migrations/20260905090000_harden_account_provisioning.sql` を対象環境に適用します。このSQLはトランザクション内で、プロフィール作成権限・RA自己同期・関係者アカウント作成条件を更新します。
4. `supabase/migrations/20260905120000_enforce_active_accounts.sql` を適用します。退寮後のアクセス制限と未読判定RPCを追加します。その後、同じ変更セットのアプリを反映します。関係者ログインAPIが未ログインでも到達可能になり、OAuth認証後の遷移先をサイト内に限定します。
5. テスト用寮生、既存RA、関係者アカウントで動作確認します。関係者ログインにはサーバー専用のSupabase管理キーと関係者パスワード設定が必要です。

この作業ではリモートへのマイグレーション適用・デプロイを実行していません。

## RAの承認方法

部屋番号の自己申告では新しくRAへ昇格しません。既存RAはそのまま保持され、承認対象外の部屋へプロフィールを変更した場合は寮生へ戻ります。

新しいRA本人がプロフィールを登録した後、既存RAが本人と部屋番号を確認してRA管理画面で部屋を追加すると、現在の利用者がRAとして承認されます。部屋がすでに一覧にある場合は、別の既存RAが本人を確認したうえで、その部屋を削除して再追加します。初代RAは従来どおり管理用SQLから登録します。

**以前の自己申告で昇格したRAは、自動的には取り消しません。** 管理者が「現在のRA」を実際の担当者名簿と照合し、不要な権限を個別に解除してください。部屋の承認操作はその部屋を現在登録しているユーザーに権限を付与するため、部屋だけでなく本人確認が必要です。

## 関係者アカウントとプロフィールの保護

通常の寮生は引き続き `waseda.jp` またはそのサブドメインに限定されます。関係者用の大学外メールは、Supabase管理APIで設定された `raw_app_meta_data.account_kind` が `service_desk` または `university_staff` の場合だけ作成できます。利用者が書き換えられる `raw_user_meta_data` は判定に使いません。

寮生によるプロフィール行の復旧作成は本人の認証済みメールと一般寮生の初期権限に限定されます。INSERT時に `role` や `account_kind` を指定して権限を取得することもできません。

## ローカル回帰確認

- `node --test tests/auth-security.test.cjs`：未ログインの関係者ログイン、公開経路の一致、認証後の外部転送拒否を確認します。
- `bash scripts/test-account-security.sh`：一時ディレクトリに新しいPostgreSQLクラスタを作成し、本人の権限昇格拒否、管理RAの承認、本人以外のメール・保護列のINSERT拒否、管理メタデータと利用者メタデータの区別を実際のSQL権限で確認します。既存クラスタには接続せず、終了時に一時クラスタを停止・削除します。
- PostgreSQLバイナリの場所が標準と異なる場合は `PG_TEST_BIN` で指定できます。PostgreSQL、Python 3が必要です。

SQLテストは認証部分に絞った最小構成のデータベースで行います。稼働環境の全スキーマとの互換性や実アカウントのログイン確認は、対象環境で別途確認が必要です。

詳細な権限と検証範囲は `docs/completion-2026-09-05.md` を参照してください。
